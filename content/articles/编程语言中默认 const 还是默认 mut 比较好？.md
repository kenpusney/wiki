# 原问题

C++默认是可变的，需要手动加const来表示不可变。而Rust默认是不可变的，需要手动加mut。那种设计更好呢？想给新编程语言设计提供参考，谢谢！

# 我的回答

 我认为默认不限制比较好。

你不知道用户什么时候忽然需要可变，也不知道什么时候需要不可变。反正编译器能够拿到这个信息在上面进行优化，随用户怎么去用呗。稍微友好一点的做法是把“赋值”这个动作换一个比较复杂的语法，同时禁用其他所有会改变操作数的操作符（比如 `+=`、`++`这些），让人明显意识到这个动作是不建议的。

引用语义场景下，参考某一篇回答的内容，可变不可变其实区别不大。但是在值语义场景下，内容的改变会直接影响对象内部结构，默认可变比不可变可操作性更强一些，但是也没必要非塞一个 `const` 进来。

我把这个做法叫做 minimum mutability。

还有什么所谓的编译时常量。现在玩的不都是编译时运行代码（CTFE）了吗，还在特别区分常量变量有点不礼貌了。

# 原作者自己的补充

Java、C++、Javascript以及大部分语言都没有真正的不可变性。每种语言的可变性概念都不一样，这个问题简直是鸡同鸭讲。本文先辟谣，再给出自己的思考。

## 没有真正的不可变

在Java/Javascript中，没有真正的不可变，只有不可赋值。例如：

```text
final StringBuffer sb = new StringBuffer();
sb.append("Hi");
```

在C/C++中，表面上是深度不可变。但事实上，只是其中一个引用不可变而已。例如：

```text
int i = 0;
const int& p = i;
print("%d\n", p);
i = 1;
print("%d\n", p);
```

所以想用const来保证线程安全，不太现实。

我个人觉得还是C++的可变性机制比较好。写一个string类，相当于同时写了Java的String和StringBuffer两个类。

## const是修饰变量还是修饰类型？

作为有C/C++背景的人，习惯性以为const是修饰类型的。但在Java/Javascript等大部分语言中，const总是和变量同时出现，理解成修饰变量也没问题。但是在C++中，const只能是修饰类型的，要不然没法解释下面的情况。

```text
const char* const p = "hi";

const string& getName() { ...; }
```

## 用var/let区分不可变有什么问题？

有答案觉得不需要有默认设定，用var/let来表示。问题是函数参数和返回类型要不要加let，像这样:

```text
fun foo(let a: &String) : let &String { ... }
```

上面这两个let真的啰嗦，还是得有默认设定。

另一个问题是，let p = ... 到底是表示下面哪种情况呢？

```text
const char* p;
char* const p;
const char* const p;
```

假设表示第二种情况，还是要在类型里面标注mut或者const

```text
let p : * const char
let p : * mut char
```

## 不可变是否能提高运行性能？

编译器能利用的可变性优化非常有限。好像只有循环不变代码外提，能从不可变性获益。考虑下面的情况。

1. 一般合格的代码都会避免在循环里面重复计算，而不会去依赖编译器优化。正常代码给编译器留下的优化余地不多。

2. 编译器可以自己识别常量。编译器不需要看是否有const标记，它只要发现变量没有被赋值过，就认为是常量。但如果全局变量跨多个编译单元，最好是加上const。

3. C++的const不是真正的不可变，只是其中一个引用不可变。编译器优化真正需要的是constexpr。例如:

```text
string a = "abc";
const string& b = a;
puts(b);
a = "123";
puts(b);
```

4. C++里面有很多后门行为。mutable变量和const_cast这两个机制的存在，导致虚假const。

总之，不可变性主要是有软件工程上的意义，而不是性能。

## 不可变带来的麻烦

最开始的设计是不可变的，但后期因为需求变更，可能会成为可变的。这时候因为不可变有传染性，会导致调用它的函数发生连锁反应，所有涉及的地方都需要修改。例如：

```text
//第一个版本
int getSize() const { return calculate(); }

//第二个版本
int getSize() {
  if (size != -1) return size;
  size = calculate();
  return size;
}
```

还有一个例子:

```text
//第一个版本
Result query() const { return doQuery(); }

//第二个版本
Result query() {
  lock.lock();
  auto r = doQuery();
  lock.unlock();
  return r;
}
```

另外模板参数类型是否需要加const，至少我从来没这样写过:

```text
std::vector<const std::string> list;
```

`std::vector<const std::string>`和`std::vector<std::string>`被编译器认为是两个完全不同的类型，之间不能相互转化。

##   不同类型变量的可变性需求分析

从功能上来说，可变变量是全功能的，而不可变是受限功能的。不可变性主要是防止在外部被意外修改，而在内部我们期待有完全的控制权。

我们可以从不同类型变量来分析需求：

1. 全局变量：无论是从权限保护还是线程安全的角度，编译器应该强制不可变，而不是默认不可变。

2. 局部变量：局部变量只属于当前函数，作用域很短。在一个很小的作用域内，很难发生意外。所以加const没有什么意义。

3. 函数参数、this：

3.1 值类型参数： 值类型传递的时候拷贝了一份，所以这个变量属于当前函数，修改值类型参数不会被外部感知。也就是说值类型参数加const毫无意义。

3.2 指针/引用参数：这里指的是指针内容的可变性，不是指针本身。传给别人可能有只读的目的，需要明确清楚是否被修改。

4. 成员变量： 大部分需求可以通过private来解决。让别人不能修改，但自己可以修改。如果是const变量，就只能在初始化列表中设置值，不如private灵活。

5. 泛型参数： 如果写`std::vector<const std::string> a; `那么就没法写`a[0] = x;`所以很少有人会把泛型参数设置成const。真是需求可能是`const std::vector<std::string> a;`

6. lambda闭包： C++中这种情况默认是不可变的，因为闭包捕获的变量实际上不是它本身，而是产生了副本。Java的策略是只能捕获final变量。

通过上面的分析，只有3.2指针/引用参数情况下区分是否可变最有意义。我觉得指针/引用参数的可变性需求强度与项目类型有相关性。如果是底层数学库可能大部分指针/引用参数是const的。而如果是上层的业务逻辑代码，估计大部分指针/引用参数是mutable的。

这是针对C/C++这样的语言的分析，所以如果是Java/Javascript，这种浅层不可变性到底有什么意义？

# 我准备补充的内容

刚看到你也回了这个提问，就着这个回答补充一下。

首先回答下你的问题，Java/JavaScript的里的final/const只是标注这个identifier不可以rebind，并非真正的constness。
```js
const a = {};
a.b = 1; // valid
a = 2 // invalid
```

其次，对于pointer来说，本身也就有 const T* 和 T* const 的区别。

```c++
const int x = 1;
const int* ref = &x;
const int* const cref = &x;
ref++; // valid
cref++; // invalid
```

至于你说，`std::vector<const std::string> a` 不能写` a[0] = x` 的问题，那不是 `const` 的锅，而是标准库对于容器的限制。标准库里的要求也是 std::vector must have a non-const, non-volatile value_type ，换句话说这个类型在目前标准库里的实现都不存在（仅以gcc15.2实现为准，C++17对于 vector 值类型的最低要求是 Erasable，但是也提到了有些操作也会有更严格的要求）。
  
接下来就对于你上文的疑问分别解答一下吧：
  
> 在C/C++中，表面上是深度不可变。但事实上，只是其中一个引用不可变而已。

这段代码里面，你只是声明了一个 const reference，那只有这个 reference 不可变，完全是符合预期的，任何通过 p 去访问那段内存的行为都必须要符合 const 的要求。你无法通过一个间接的引用来去限制一段内存是否可变——更何况也基本没啥编程语言可以做到这点。

> const是修饰变量还是修饰类型？

这就要看你认为的 constness 是什么。是运行时的 .rdata 只读数据段（比如C++的字符串字面量），还是 C++ 这种修饰类型来保证 const 类型的数据不可变，还是像 Java/JS 那样不能 rebind。还是更进一步地如zig的 comptime const 或者 C++ constexpr 一样表示编译期数据。

C++里没有能不能rebind这个问题，引用是直接限制死了不能，指针是为了兼容C，而自定义类型的赋值运算是可重载的，行为由用户自己定义，也可以= delete 干掉这一操作了。

> 用var/let区分不可变有什么问题？

这点上我跟你想法一样，更不用说隔壁 JS 的 let 是拿来声明可变变量的。

> 不可变是否能提高运行性能？

constexpr 不是拿来做编译优化的，是进行编译期计算的。这部分操作其实还是你作为程序员通过编译器的能力来手动优化，自动优化是更后面阶段的事情了。

> 不同类型变量的可变性需求分析

第1点，如果出现了初始化依赖或者需要延迟初始化（lazy initialization），你全局不可变怎么解决呢？可选的思路是把初始化什么的都交给一个托管的框架，那大概率会得到一个C# ，或者实现了Project Valhalla的Java。

第2点，C++里的 const 有一个点是，非 const 类型为了兼容 C 是可以不初始化的，但是 const 类型必须要初始化。这是C++里有 const 局部变量的一个好处，其他的嘛，参考上面那个stackoverflow的回答。

第3.2点，“需要明确清楚是否被修改” 交给编译器去判断，然后再去标记被调用方。因为除非你给到对方的是 .rdata 段的数据，对方改了会导致 segment fault，否则总有任何脏办法在你明确标注是只读的情况下修改你的数据。

第5点，如果你确实泛型类型需要使用到 const 某类型，完全可以decay或者remove_cv以后再往上塞修饰符，参考 iterator_traits 的操作。这种时候远比考虑在泛型参数上用可变还是不可变来的好，约束是接口提供者提前设计好的，不用用户操心。

另外 C++ 模版只是模版，与其他编程语言的泛型类型差别还挺多的，轻易不要胡乱模仿。

第 6 点，C++有引用捕获，当然这个跟constness没太大关系，只是提一句。这样就能做到在闭包里改变上层对象的值。Java虽然有effectively final限制，但也可以通过捕获一个长度为1的数组的方式，在闭包里改变上层对象的内容——这个也是听 Rfx 大佬说过的实践。

所以还是保持我在我回答里那个 minimum mutability 的观点。也即不区分 const 和 mutable，不允许 rebind，引用必须初始化，不支持除赋值以外的的其他改变内存值的操作。不过这只是设计思路，最近还在糊type checker，要等成型以后才能做更深入的验证。
