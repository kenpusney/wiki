## Six Pillars of Database

我这里总结了6点关于一个数据库所需要具备的核心能力：

- 首先是要有单一信源
- 其次是要能支持并发协作
- 能够稳定地提供查询和报表
- 支持全方位的访问控制和审计
- 有完善的数据备份和恢复功能
- 对不同类型的数据提供质量和生命周期管理

## 单一信源

数据库并不只是单纯“存储”数据，也不只是系统级别的连通。通常一份数据出于不同业务原因我们会有多份拷贝保存在不同的系统中，那么我们需要明确三个问题：

- 1）这份数据最终以哪个系统为准？
- 2）如果两个系统不一致，按什么规则修复？
- 3）修复过程是否可追溯、可解释？

因此要明确“谁是权威源”，其他系统是“复制件/衍生件”。

这是在解决我们前面提到的“对不上”的问题。

## 并发协作

多个系统集成，以及多个用户协作的时候很容易同时触碰到同一份数据。比如：
- 哪天Freelander发售了，大家线上抢预约，同样一个名额结果被两个用户抢到；
- 或者说我们的车辆出了告警，有两个人同时处理并且提交成功了。

数据库系统应该需要一套机制来避免这种情况，让多系统或者多用户并发操作时不会互相踩踏。

这里也就避免了一部分“对不上”、“不敢改”和“丢数据”的问题。


## 查询与报表

这个就很简单了。

一个数据库系统应该允许用户按照自己的需求去检索数据，而不是继续像是上面档案柜的例子一样去一个个翻找档案卡片。并且这一步骤应该是能够稳定自动化的。

右边这里是英剧《是，大臣》里的一段对白。说是英国政府在准备构建一个全民信息数据库，Jim Hacker在接受采访的时候被问到了这么一个问题，你们把数据存进去了，总是要取出来的——其实是要引导他回答这个数据控制权和访问权的问题，但是Jim Hacker为了避免正面回答问题就在绕圈子，说不一定要取出来。然后主持人反问说，你们花了两千五百万英镑专门为了收集数据和信息结果啥都不干是吧。

Hacker最后憋出来了一句“There will be safeguards”。

## 访问控制和审计

这就涉及到了我们接下来要提的这一点。

数据存下来以后谁有权限访问，以及谁进行了哪些方面的变更，尤其是我们现在有了更严格的数据安全法和个人信息保护法以后，对于客户的信息控制也有了相应的要求。

审计记录不仅仅是为了确认谁做了什么，更是追溯事件记录和解决争议的重要参考。

## 数据备份和恢复

上周 Arch Lead 也组织了一个 DR 相关的会议讨论过类似问题，当然备份恢复是个更广泛的概念。通常来说也是面临系统故障以后的补救措施。

通常来说在业务级别我们就需要定义两个关键的指标：

- 允许系统停机多久，也就是RTO
- 允许系统丢失多少数据，也就是RPO

比如：
- 对订单与结算：很多团队更害怕“丢数据”，因为丢了以后很难补齐、也很难对账。
- 对用户体验敏感的系统：很多团队更害怕“长时间不可用”，因为客户体验和一线压力会立刻爆发。
- 对实时系统，比如车联网告警：很多团队更害怕“写入完全堵死”，因为会引发链路级联故障。

对于一个数据库系统最基本的要求也就是能备份、能恢复，并且可演练。这也是在解决我们前面提到的“丢数据”的问题。

## 数据质量和生命周期

我们能够有效地操作数据、查询数据，也有了稳定的备份恢复功能来保证数据库长期有效运行了，那接下来我们要关注什么呢？

首先是数据的业务属性和定义。

举个例子，我们Domain里的“车辆ID”是什么——不同系统内部可能为了脱敏会使用自己的ID，但公用的必然是车辆的特殊标志。

数据库与数据模型要绑定业务定义，并且形成可维护的“数据字典”。

通常来说我们要处理的数据也是分为不同的类型和层级，比如：

- 主数据
- 事务数据
- 事件数据

主数据通常变化不频繁，但一旦错了，影响面非常大。所以主数据需要有与业务紧密绑定的统一定义和口径。当我们提到某个概念的时候大家共识上是一致的。

事务数据是用来记账用的事实记录。主要是各种单据或者流水记录。事务数据关键的是要保证每一条记录都能准确无误地保留，并且沿用固定的状态转移流程。比如一个已支付的订单，不能跳回待支付。

事件数据包括诸如车联网遥测、告警、日志、点击埋点这种与时间密切相关的数据。通常来说不是每一条都必须要审计，但是要能够快速过滤出关键的那部份（比如在车辆上报数据里拿到告警的信息）。

事件数据发送频率高，量大，因此相对于前两种，也就需要考虑一个分层的存储策略——必要的时候部分内容应该可以归档到冷存储中。

这种层级策略能够让我们更好组织数据，避免大量内容堆叠在一起造成的数据混乱和查询效率低的问题。

## Six Pillars of Database

我们再来看一下这6个支撑点：

- 首先是要有单一信源
- 其次是要能支持并发协作
- 能够稳定地提供查询和报表
- 支持全方位的访问控制和审计
- 有完善的数据备份和恢复功能

这六个方面支撑我们解决前面提到的”对不上 /找不到 /不敢改 /太慢 /丢数据“等问题。

## 什么是数据库？

这是我们根据上面的内容导出的数据库定义，

数据库 = 一套“存储 + 组织 + 查询 + 保护 + 恢复”的系统，能够允许多个人、多系统在同一份数据上协作，而不把它用乱。

## 有哪些类型的数据库？

在 Domain 内部我们使用的数据库有以下几种：

- 作为账目系统以强一致事务管理的关系型数据库 PostgreSQL
- 按照业务对象管理数据，应对结构灵活的数据类型的文档型数据库 MongoDB / DocumentDB
- 高吞吐量能够按照关键属性快速响应结果的 DynamoDB
- 低延迟的内存数据库 Redis / ElastiCache

接下来我们会分别给大家介绍这四种数据库。

## PostgreSQL

接下来我们聊关系型数据库的代表——PostgreSQL。

首先可以看到这条评价“世界上最先进的开源关系型数据库”。

说到PostgreSQL呢，很多人第一反应是 '它和 MySQL有什么区别？'

我们就从PG的索引设计、一库多用、扩展生态这些方面展开介绍。

### 索引设计

MySQL用的是聚簇索引，就是数据按主键排好序，物理上有序存在磁盘上。高并发写入时，这就成了瓶颈。

PG所有索引，包括主键，都是非聚簇的。数据存在一个叫Heap的无序文件里，新记录直接追加，不需要维护物理顺序。写入更灵活。特别是在金融交易系统、实时分析这种混合读写的场景下，性能会更稳定。

打个比方——MySQL像一本按目录排好的书，PG像一个贴了标签的储物柜。

它支持四种索引类型，每种针对不同的数据。

### 一库多用和生态

PostgreSQL 支持多种数据类型。

JSONB——这是PG的杀手锏。它不是简单的文本字段，是二进制存储，查询速度比普通JSON快3到5倍。可以在JSON内部字段上建GIN索引，查询速度接近关系型字段。

PostgreSQL有非常丰富的官方认证的扩展，有94个，我挑几个说：

PostGIS –地理信息处理

PGVector –向量相似度搜索，AI application可以直接在数据库里做Embedding检索

TimescaleDB –时序数据自动分区和压缩

### PostgreSQL AWS 生态

PostgreSQL在AWS上有两个选择：RDS PostgreSQL和Aurora PostgreSQL，这两者的架构完全不同。RDS是AWS帮你运维的PG'，Aurora是'基于PG协议重新造的数据库'。

RDS是托管的原版PG，存储架构用的是EBS-elastic block store,类似于云端的移动硬盘或虚拟磁盘。在RDS的结构中，数据库引擎和EBS磁盘是物理分离，但通过高速网络连接的。

RDS和 aurora写入磁盘的区别不同，rds是传统的方式，每次数据变动，数据库都要把每页纸重新涂改在写入磁盘，但是aurora类似于微信语音，不发送整页纸，只发送一张张变动指令redo log，底层的存储系统在收到这些指令后，自己在后台就把报告改好了。所以在高并发写入时候，rds会遇到致命的网络和IO瓶颈，aurora的吞吐量是标准PG的三倍。

比较大的差异RDS做多可以有5个只读副本，aurora则有15个，why？

RDS是基于物理卷的异步复制。每增加一个只读副本，主库都需要通过网络向该副本发送完整的日志数据包。负载压力很大，主库像一个快递员，每多一个副本，就要多送一个快递。数据同步会延迟。

Aurora采用了云原生存储架构。工作原理：主库和15个副本都共享一个底层的虚拟化存储集群。主库只往存储层些redo log，而不直接发数据给副本。

在费用方面，Aurora 的实例费比 RDS 贵大约 20%，这还不算完，它还额外按读写操作收 I/O 费用。写入量大的业务，I/O 账单可能会比较高。

## MongoDB / DocumentDB

接下来我们聊文档型数据库的代表——MongoDB。MongoDB非常适合内容管理系统、快速原型开发、IoT 数据采集等场景中，它的「灵活模式」正在成为开发者的默认选择。


### MongoDB 索引

MongoDB也有非常丰富的索引类型可供选择，主要是为了灵活匹配具体的适用场景。你可以选择组合或者单独匹配某些内容。

| 索引类型 | 适用场景 | 核心优势 |
|---------|---------|---------|
| **Single Field** | 单字段精确/范围查询 | 简单直接，90% 场景够用 |
| **Compound** | 多条件组合查询 | 一次索引覆盖多个字段，减少扫描 |
| **Multikey** | 数组字段查询 | 自动展开数组元素建立索引 |
| **Text** | 全文搜索 | 内置分词+倒排索引，支持多语言 |
| **2dsphere/2d** | 地理位置查询 | 配合 `$near`、`$geoWithin` 做 LBS 应用 |
| **Hashed** | 分片键均匀分布 | 避免数据倾斜，适合高并发写入 |
| **TTL** | 日志/会话自动过期 | 自动删除过期文档，运维零成本 |

**一个关键差异**：MongoDB 的索引是「按需创建」的。你不需要像关系型数据库那样预先设计完整的主键/外键体系，而是根据实际查询模式动态添加索引。这在业务快速迭代的场景下非常友好。

✅ **适合场景**：
- 业务模型快速迭代，字段频繁变更
- 数据天然嵌套（如用户画像、商品详情）
- 需要水平扩展应对海量数据/高并发
- 想一站式集成搜索、向量检索、实时同步

比如 当前系统 存储车辆上报的实时数据用的就是 DocumentDB，也就是 AWS 兼容 MongoDB 的实现。

❌ **谨慎场景**：
- 强事务一致性要求（如金融核心账务）
- 复杂多表关联查询（虽然 `$lookup` 能做，但性能不如 SQL JOIN）

### MongoDB on AWS

在AWS上也有两套可选的MongoDB，其中一个是兼容MongoDB但是底层类似Aurora的DocumentDB，另外一套是由MongoDB官方维护的MongoDB Atlas（可以在Marketplace选购）。

DocumentDB 兼容了大部分 MongoDB 的功能，包括最近实现的向量索引和检索功能等等。所以在不是非常依赖MongoDB专有特性的情况下，优先还是推荐使用 DocumentDB。

## 总结

我们今天的session就这些内容，接下来再做一个简单的总结：

- 数据库的第一价值不是“存”，是让多系统多角色在同一份数据上协作时依然可信。
- 选型先从业务问题出发：数据形态、访问方式、规模与风险
- 多库并存不是混乱，前提是：明确权威源、明确复制与衍生、明确恢复与审计。
