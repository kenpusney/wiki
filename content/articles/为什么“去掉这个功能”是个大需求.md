几米Kimmy 轻技术 *2020年2月17日 22:40*

经历了好几波的产品研发，大致上感觉到，大部分非软件行业人员对于软件开发的概念仍然处于非常原始的阶段。通常一个针对企业用户的软件产品会是有一套标准化的功能，然后在客户实际需求的基础上，进行二次的开发；根据客户的需求量进行评估和报价，并安排后续的交付和实施工作。

## One Law to Rule Them All

大部分人对于软件系统的期待是集成度越高越好。于是知名的 JWZ 也基于此提出一条定律（Zawinski's Law <sup>[1]</sup> ）：

> Every program attempts to expand until it can read mail.
> 
> 每个软件都在尝试扩张他的功能，直到可以拿来读邮件。

至于为什么会这样，这个定律的下半部分做了解释：

> Those programs which cannot so expand are replaced by ones which can.
> 
> 做不到这样扩张的那些软件会被能做到的给替代掉。

对用户来说也是这样的。一个系统里面能够完成的事情，尽可能的不要做迁移放到更多的地方去做。于是你会看到一些 Chrome 的专家用户会在他的浏览器里面尽可能多添加可用的插件，或者是看到一些 SaaS 平台总是能更新一些你意想不到的功能（比如最后都做成了能发心情能评论的 SNS）。

插一句，Jamie Zawinski 是上世纪软件业的传奇人物，也会是我们圣战简史系列的常客。他留下了包括前面的加文斯基定律在内的很多经典名言，比如下图：

## “我不想要这个功能”

但这个时候就出现问题了。

C 端用户你怎么折腾都行，毕竟容忍度比较高，而且还可能会接受你的一番产品哲学的安利，吹捧起来。可是面向企业用户（B 端）的产品就没这么容易了。

C 端用户不想要这个功能，不去用就好了，你可以不发朋友圈，但作为一个个体是没办法说服微信团队干掉朋友圈这一块儿的。但 B 端用户要说，我不想要这个功能，你无论如何也得想尽办法把客户的需求给实现了。需求是否可行这个是额外讨论的问题，但一旦一个需求从“ **我想要 xx** ”变成了“ **我不想要 xx** ”，也是能够头疼到一波人的。

从客户的角度来说他会觉得，我不要这个功能你去掉就好了，还能省工作量，有什么难度呢？

## 可定制性 Customizability

> Custom（习惯） - ize（变成…） - ability（的能力）

我们用这么一个合成词来定义软件在这方面的能力，也即这个软件能够改变到符合用户的使用习惯的能力。改变到符合用户习惯这样一个过程，就是 **定制化** （Customization）。

定制化一些多出来的功能，很简单嘛，我们继续开发就好了。而且如果这个需求普遍，很可能就转成后面产品的一部分发布了。接下来的客户也能享受到这个功能，又能提升产品的承载能力，当然是大家都喜欢的。

可是客户明明说的是“我 **不想要** xx”嘛！怎么办？

- 删代码的话，那就得单独为这个客户维护一套专用的代码了；
- `if client is Some Corp then don't do this` ，妥妥的需要增加工作量和管理成本的呀。

那么除了这种强行增加系统复杂度的办法，还有没有更好的做法来应对“去掉这个功能”？

### 功能开关

最简单最直接的做法，是给一些大块的功能做开关。通常这种的可行性是，这块功能比较独立，不会收到周围所使用的功能的影响。即便是关掉，对于整体的软件体验并没有丧失。比如一个 OA 系统，可以把评论给干掉，并不会影响其主要功能的运转，这种时候，功能开关能够比较方便的去控制这样层级的定制化。

另外比如通常做管理系统的会通过这种方式来控制定制。毕竟本身管理系统的权限也是有一套类似的分角色/场景的开关的。

### 主题化

另外一种需求可能会更复杂一些，客户的需求其实并不只是在于大块功能上，比如，展示细节上，“把 xxx 上的 yyy 隐藏掉”。这种时候其实更多的是需要抽离展示逻辑和应用功能，然后把展示逻辑也变成配置（主题），通过定制主题内容来改变呈现效果。

这个其实也有一定的强要求的。

- 首先要有灵活的视图能够容许定制主题；
- 其次背后对应的数据模型也必然是有一定的灵活性来适应主题的变化，甚至能够允许用户来定义视图绑定的数据模型（参考金数据 <sup>[2]</sup> ）；
- 另外这些关键的主题配置都能够绑定到足够完善的功能来保障使用；
- 通常做到这样灵活的系统，背后一般也会有一套定制视图主题的工具链，才能更方便做这些事情。

### 配置脚本

然后更复杂的就来了。比如，客户希望在某个地区的用户访问系统的时候不给展示某些功能；或者比如当访问用户达到某些数量之前不显示某些功能等等。这个时候，要么让客户选择每个定制功能都做专有开发，要么就必须加入一些逻辑处理能力来增强配置系统。

这一步做到了当然基本上没啥可以难倒的客户需求了。但对于软件的研发和维护团队来说仍然增加了很多问题。我们知道，一个支持 if 分支和递归的构造，基本上就是图灵完备的了。所以，这样一个配置系统无疑会成倍地增加系统的复杂性。另外还需要慎重是，配置系统的学习成本，以及用于组合软件功能的配置和软件具体功能组件间的平衡。

## 格林斯潘第十定律

当然了，另外一个格林斯潘第十定律（Greenspun's tenth rule <sup>[3]</sup> ）决定了，这条路是大部分存活下来的软件系统的宿命：

> Any sufficiently complicated C or Fortran program contains an ad-hoc, informally-specified, bug-ridden, slow implementation of half of Common Lisp.
> 
> 任何 C 或 Fortran 程序复杂到一定程度之后，都会包含一个临时开发的、不合规范的、充满程序错误的、运行速度很慢的、只有一半功能的 Common Lisp 实现。

翻译成人话就是，任何一个复杂的软件系统最后都要通过一个实现的很烂的脚本来做配置。

## 复杂系统的设计

你看其实 **加文斯基定律** 和 **格林斯潘第十定律** 本质上再说同一件事情，一个复杂的系统最终会走向不可控制的方向。

而在早些年，Web 2.0 概念还尚火的时候，其实还没这么可怕，那个时候出现了一个概念，叫 mashup（糅合），通过共有接口和开放 API 来组合集成实现复杂功能。所以你现在看到的大部分互联网产品的概念和形式都是在那个时候形成的，比如 IFTTT <sup>[4]</sup> 。这种产品形式非常符合 unix 哲学，对于专家用户是友好的。

IFTTT: if this then that

但大部分互联网用户都非专家用户的情况下， 一个集成度恰当而且学习和使用成本不高的产品才能作为核心工具而存在。想要达成实现这种效果，要么你选择自身作为一个开放的产品存在，并提供机制跟其他产品集成；要么你自身实力够强大，能够作为一个封闭的平台承载大部分这方面的功能——而后者似乎是目前大部分互联网巨鳄采取的做法，都想维护住自己的生态。

## “去掉这个功能”

回顾问题。去掉一个功能对用户来说感受上可能没那么多不一样的，但考验的是软件人员对系统整体的设计和思考。无论如何，从各方面角度来说，这都是一个典型的需求，无论是软件设计之初就考虑进来，还是对客户实施的过程中考虑进来，对系统的设计都是有非常明显的影响。如果不想让系统变成一个充满 if-else 的屎山，越早越越好。
