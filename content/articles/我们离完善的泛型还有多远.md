最近 Golang 的泛型方案终于有了飞跃式的进展。我们能在Go2 Playground <sup>[1]</sup> 上面试用一下。

Golang 的泛型是个老日经话题，每次提及的时候都不忘带上。当然 Go 本身比较克制，按现在阴阳怪气的说法，叫做“ **大 道 至 简** ”。所以对于泛型这种极其影响设计的东西当然要慎重考虑，妥善处理。于是我们长期看到，热门的静态类型语言里面之后 Golang 没有对泛型的支持。

2016 年年末，当知道 Concept 不会进到 C++17 的时候，我写过一篇文章 <sup>[2]</sup> 捎带着提了一下当时的情况：

> 1. 我们希望 JS、PHP 是 static typing，甚至就算是 Go 那种 structural typing 也好。
> 2. 我们希望 Go 有泛型。
> 3. 我们希望 Java 有 Reifiable 泛型， 至少像 C#那样。
> 4. 我们希望 C#有 Parameter pack，至少不再写上十几个 Func、Action 和 Tuple 类。
> 5. 我们希望 C++有 Concept，有 template type deduction，有 any、optional 和 variant。
> 6. 然后我们把 Haskell 编译到了 JS。———— 《在知足的路上越走越远。》

## 泛型（Generics）是什么

泛型 <sup>[3]</sup> 是 **参数化多态** （Parametric Polymorphism <sup>[4]</sup> ）的一种实现，是多态的一种。这里的多态不是 **面向对象编程** 中的“多态”，面向对象的“多态”只是 **子类型多态** （Subtyping Polymorphism <sup>[5]</sup> ），多态的三种类型之一（另外一个是 **特设多态** ，Ad hoc Polymorphism <sup>[6]</sup> ）。当然目的是一致的，就是通过单一的接口服务不同的类型，或者通过单一的符号表示多种类型。

> 多说一句，“ **泛型** ”（Generics）通常讹误为“ **范型** ”（Paradigm）。前者是指的是泛化类型，后者则表示一种模式或者规范来作为参照分析，也会叫成“ **范式** ”。如果理解泛型真正的意思，就不会出现这么明显的误解。

与子类型多态的动态分发（dynamic dispatch）不同，泛型是通过把类型作为参数，通过对相似的类型提供统一的操作来达到多态的目的，所以通常也叫参数化类型。比如如果我们要对不同的数值类型提供一个最大值的函数，在没有泛型的时候只能通过 **重载** （Overloading，特设多态的一种）来实现：

```
// Golang 不支持重载的，以下是java代码

int max(int a, int b) {
  return a > b ? a : b;
}

int max(float a, float b) {
  return a > b ? a : b;
}
```

你看要这样下去得多麻烦。更不用提在不支持重载的情况下你给每个函数都安一个不同的名字，想想 C 语言 `math.h` 里的 `abs` 和 `fabs` 吧。

这个时候泛型的需求就出现了，上面两段代码除了参数的类型不一样以外整个结构和内容都完全一致，那通过泛型我们就可以简单把这部分代码简化成一段：

```
<T>
T max(T a, T b) {
  return a > b ? a : b;
}
```

这里的 T 就是类型参数，通过这样把类型给参数化以后，我们的 max 可以 **接受不同类型的数据** 了，也可以 **表示对不同数值类型的数据求最大值的函数** 了，完美达成了多态的效果。

但这里有个问题，如果我往里面塞得是一个 `new Object` ，按 Java 的规则， `Object` 是不能比较大小的，所以这里就傻了，编译不过。像是早些年的 C++，这里直接就给你吐一大堆看不懂的错误就完了，Java（和其他的编程语言）在这里往前多走了一步，在看到这段代码的时候就会判断是不是能够进行比较，如果不行，直接这个方法就编译错误。如果你要在上面进行什么操作，一定要告诉编译器，这里我需要比较两个数据了。

也就是说我们在类型参数上一定要给出来约束。像最简单的 Vector，可能不会对类型有什么特殊的要求，但大部分情况下都还是需要做一个基本的限制。

在有了类型约束的情况下，就可以这样写代码了：

```
// 原谅他，Java目前没办法使用基础类型作为类型参数，
// 也不能用非接口之外的方式表示约束
<T extends Comparable>
T max(T a, T b) {
  return a.compareTo(b) > 0 ? a : b;
}
```

等到你在 `max` 两个 `Object` 的时候，编译器自然会告诉你这是个错误。

看这样用起来泛型是不是特别好用，非常完美？

才怪嘞！！！

## Reifiable Generics 和特化（Specialization）

设想这样一个场景，我希望处理两个不同的集合，但他们因为不是由我所控制的，如果想要设计一致性的接口，比较好的做法是通过重载来实现。比如以下 Java 代码：

```
void process(List<Foo> foos) {
 ...
}

void process(List<Bar> bars) {
 ...
}
```

很不幸，Java 编译器报错了。原因是这两个 `process` 方法有共同的擦除类型。这就是 Java 这种泛型实现机制。在前面 `max` 的例子中，我们合并了两个方法， 如果是像 C++/C#这些编程语言，对于 `int` 和 `float` ，实际会产生两个不同的函数，分别来处理这两个类型，但是 Java 为了省事儿，再加上本身参数做了约束，所以只要保留一个方法就能达到同样的效果了。对于泛型类，处理方式也是一样。于是在 Java 运行时， `List<Foo>` 和 `List<Bar>` 没有什么本质的区别，都是同样的 `List` ，因为 Java 编译器在这个过程中做了一次类型擦除（Type Erasure），对于上面的 `process` 函数，类型擦除的结果是一致的，运行时根本没办法区分。

所以遇到这种问题 Java 几乎是没办法解决的。同样是 JVM 平台的 Kotlin 在解决这种处理的时候引入了 `refied` 关键字，编译和运行过程中通过判断传入对象的类信息再来做分发。而 C++里面实现泛型的机制是模版，对于每一个模版参数，都会进行实例化展开，所以只要传入的模版参数不同，就一定会实例化成不同的代码片段。

Reifiable Generics 虽然能够解决这个问题，但与此同时也带来了另外的缺点，首先是每个类型都要生成代码也会导致编译速度变慢，其次生成的对应代码会导致生成的对象文件非常大，再则，因为每次实例化都需要完整生成代码，那编译器就需要知道足够多的代码信息，所以像 C++模版这种设计，基本上是必须开放源码才能用。.NET CLR 通过运行时实现 Reifiable 避免了这些问题，但结果就是运行时实现非常复杂。

Reifiable 实现了每个泛化之后的代码片段都是独立的，但是这还是不一定能解决某些问题的。就像我前面的文章说的，客定需求总是在的，能不能做到对于某个类型的泛化换成我自己的实现呢？

这就是 **特化** （Specialization）做的事情。

当然了在特化之上还有 **偏特化** （Partial Specialization），只对部分参数做特化处理。道理一样，不再赘述。

## 越走越远

今天跟培神聊 Golang 的泛型，他整理了一个发展路线 <sup>[7]</sup> 。Go 只位于最基础的那一层上，实现了特化也只是勉强提了一层。而往下还有非类型模版参数（NTTP）、高阶类型、类型参数包、concept map 和 static if。

已经开始逐步魔幻化了，但是还是非常有必要的。比如我们来看 Golang 和 Rust 的数组：

Golang：

```
var a = [5]int{1, 2, 3, 4, 5}
```

Rust：

```
let a: [i32; 5] = {1, 2, 3, 4, 5};
```

这两个编程语言的数组类型都是带着数组大小的，Golang 里， `[5]int` 跟 `[6]int` 是完全不同的类型，Rust 里也一样。但是这样使用常数类型参数只存在于数组中，相当于是类型设计上专门给数组类型开了个洞，是非常损失一致性的。而本身作为类型组成的一部分，常数能够加入类型中会适用非常丰富的场景。

总之，C++ 远在 C++98 版本就实现这个功能了。以至于原本设计用于泛型的模版系统甚至是图灵完全的。

另外比如类型参数包（parameter pack）。大部分的编程语言（比如 C#、Scala 等）的“元组”都是实现了手动实现了很多个不同长度泛型参数的版本，而在 C++ 的实现则非常的简单直观：

```
// http://eel.is/c++draft/tuple.syn
template<class... Types>
class tuple;
```

这里就通过参数包实现了可变长度的类型参数。C++ 就可以通过这样一个类来实现类型安全的元组。

更进一步的玩法就是把类型和泛型类都当成第一类值（first-class value），这样就可以在编译时组合和操作类型。也就达成了高阶类型（Higher Kind Type，HKT）。至于 concept map 和 static if 这些更进一步的操作。

## 成熟的泛型

老实说这也不是必然走的路。像培神前面的列表，直到 C++20，C++才有类型约束（Concept），但在这之前除了 concept map 之外的内容基本已经有了。这其实就是最早的 ConceptC++在 2008 年左右的设计。

我们能看到泛型编程从一个基本的复用工具、到建模工具、到演变成为用于完善类型系统的一部分。整个过程漫长艰辛，C++、Haskell、Rust 踩过了无数的坑。 **C++** Concept 从 C++0x 时代一直到 C++20 才勉强加进来 constraints 一部分， **Java** 的 Project Valhalla（对 Reifiable 和特化的支持）现在还在 proposal 阶段， **Rust** 的非类型泛型参数也还没完全成为成熟的语言特性。

但是至少能看到的是大家都在接受了这部分思想，现在连 Golang 也作出改变了。
